# The pipeline - eight stages

Contract between stages: files on disk. The Orchestrator (you) owns `canonical.json`, runs deterministic scripts, dispatches isolated sub-agents for judgement work, and adjudicates verdicts. `helpers/run.py` runs the deterministic spine (Stages 0-7) in one command; the agentic steps are layered around it.

> **Where the files live - the three-folder project layout.** A project folder holds exactly three numbered top-level folders: **`1. Input`** (the broker's source files), **`2. Work Files`** (every internal artefact - this IS "the work dir", `--work`) and **`3. Output`** (only the four client-facing deliverables). `run.py --project "<root>"` derives all three and creates them. Throughout these docs `work/<x>` means `<the work dir>/<x>`, i.e. `2. Work Files/<x>`; nothing about the work dir's CONTENTS changed, only its name and the fact that the deliverables no longer sit inside it. The legacy `--folder <inputs> --work <workdir>` invocation still works and still delivers to `<work>/deliverables`. Full setup instructions: SKILL.md "The project folder".

> **Running a single stage directly:** prefer `run.py` (it wires every stage correctly). If you do call a stage by hand, note the per-script CLI differs: `intake.py <folder> --out-dir <work>` (also accepts `--folder`/`--work` aliases), `merge.py --records … --source-dir <inputs> --out <canonical>`, `enrich.py <canonical> --geocode …`, `gate_runner.py <subcommand> …`, `build_dashboard.py <canonical> --out <html>`, `render_qa.py <html> --out <dir>` (`--out-dir` alias), `deliver.py --canonical … --html … --ledger … --out-dir <output dir> [--marker-dir <work>]`. `--help` on any script lists its flags. Every stage still takes the work dir as a plain path - none of them cares what it is called.

## Parallelism
- Stage 1 fans out one sub-agent per source file or per-city cluster (the reference is organised Bratislava / Budapest / Pilsen).
- Stage 4 and 6 judgement reviewers run as parallel isolated sub-agents, dispatched concurrently (all of a phase's `Agent` calls in one message) against a **frozen** artefact (`gate_runner.py freeze` / `freeze --check`) so every reviewer judges byte-identical bytes. One gate = one agent; parallelism strengthens independence (no verdict exists yet to bias another). See `reference/gates.md` "Reviewer dispatch contract".
- **Plain-chat with no sub-agent dispatch is a labelled DEGRADED mode**: verdict files are still written but independence is weaker; say so plainly.

## Re-runs
Edit, do not rebuild. With updated inputs, re-do only the affected stages and re-inject from `canonical.json`. The QA window is a **SINGLE review pass, LOOP-DRIVEN by the spine** (SKILL.md exits 14/15): spawn the reviewers ONCE at exit 14, implement every blocking finding plus any advisory that is one edit and changes what a reader concludes, deliver. **A second review round is never correct, and there is no mechanism for one** - `qa-round record` writes into one round slot and a review file that changes afterwards FOLDS into that round as extra findings, which is what keeps a re-dispatched garbled review recordable without buying back a second round. The isolated reviewers PROPOSE findings (dispatched at exit 14 from the rendered prompts), the orchestrator IMPLEMENTS them and RECORDS each repair (`qa-round resolve --id <id> --because "…"`, or several at once with `--batch <file.json>`, at exit 15, a fix loop WITHIN the round that never re-dispatches a reviewer); the spine runs `record`, `deliver` and `final_gate` itself. There is no adjudication round and no verdict-word gating. `final_gate.py --qa-state <work>` BLOCKS while any `blocking:` finding has no recorded resolution - a false claim must not ship because the review pass ended - and CARRIES every advisory finding into the Gaps Report's "Known limitations", which ships. The mechanical gates and the freeze are unchanged hard blockers (`reference/gates.md`).

`run.py` resumes BY DEFAULT (`--no-resume` recomputes everything): it skips any stage whose output is already current (intake, per-file extract, merge, enrich, build) and recomputes only what a changed input invalidates. The gates and the freeze are never skipped, so the mechanical and judgement verification still runs in full on every resumed build. Built for sandboxes with a short shell cap (e.g. Cowork's ~45s) and for the vision re-run: a killed or vision-interrupted run resumes instead of restarting from scratch.

**Agentic handoffs are exit codes; after ANY of them, do the one mapped action then re-run the SAME command (resume continues):** exit 3 = a brochure deck, a tracker or a region label needs interpretation; exit 8 = web enrichment (geocode/POIs/drive-times); exit 9 = photo-match (textless brochures that are photos of known properties); exit 10 = cross-source adjudication, every kind in one round-trip (GREY-zone match pairs AND already-merged auto pairs offered for confirmation -> `work/match_decisions.json`, value conflicts -> `work/field_decisions.json`, `reference/matching.md`); exit 11 = a supported non-bundled dashboard language needs a one-off chrome translation; exit 12 = free-text DATA translation (`reference/localisation.md`); exit 13 = clarification questions (`work/questions.json` -> `work/answers.json`, each asked ONCE; the kinds include one `combine_policy` question per field whose figure several cards print as separate lines, `not_available` for a building the source marks let/sold, and the blocking `arithmetic_basis`); exit 14 = the independent QA review (one blind agent per rendered `work/prompts/g-*.md`; the full per-property media view is written first, then reused while its inputs are unchanged); exit 15 = blocking QA findings unresolved (`qa-round resolve`); exit 17 = the MASTER LIST, the user's scope decision, which fires once per candidate set and re-opens only when the inputs set changes (`reference/master-list.md`). Each writes its manifest to the work dir, caches the sub-agent's decision keyed by a stable hash, and resumes byte-deterministically. None fires when its work is empty (a pure-brochure run never hits 9/10; a single-source run never hits 10). SKILL.md's exit table is the authoritative per-exit action list.

**Exit 16 is NOT one of those handoffs, and it is listed here so it is not mistaken for a missing one:** it is a REFUSAL TO START - `work/overrides.json` and/or `work/repairs.json` hold entries the loader rejects, every fault is printed in one pass, and nothing has been changed. No stage has run, so there is no manifest, no sub-agent to dispatch and no cached decision; `gate1_scorecard.md` does not exist yet and must not be read. The re-entry contract above does hold: do the one mapped action, then re-run the SAME command. That action is **FIX or DELETE the named entries IN PLACE in the file each fault names** - never append a new entry, because the file being rejected is the file to edit. Per-exit detail: SKILL.md's exit table.
